# 实施方案：拍记待办误提取修复 + Spark 跟进翻译回灌全文

> 日期：2026-07-22
> 状态：待实施（本文件仅为方案，不含代码改动）
> 作者：调查 + 方案由 agent 撰写，已对照代码核实

本方案覆盖两个**互相独立**的问题，可分开 review、分开上线：

- **改动 A**：新闻类拍记被错误提取出"第三方待办"（如"警方继续追查""反黑组跟进调查"）。根因是待办提取 prompt 的语义边界缺失。
- **改动 B**：Spark 在"翻译一下 / 展开说说"这类短跟进里，手里没有文章正文，因为拍记注入 prompt 时有两层截断。用已存在的 `[来源N]` 引用机制精确回灌全文。

两个改动都触及**共享文件**，因此都影响 **Notiee（免费）** 与 **Notiee+（BYOK）** 两个 target，需按 AGENTS.md §2 双 target 验证。

---

## 背景与根因（已核实）

### 改动 A 的根因

链路：拍照 → OCR → 文本结构化 prompt 让模型输出含 `todos` 字段的 JSON → 直接落库成待办。

问题出在 `Notiee/Services/AIPromptProvider.swift` 的待办字段措辞。简体分支（`buildTextPromptZHHans`，约 `:177`）：

```
"todos": 如果文本中包含任何需要执行的任务或待办事项，请提取为一个字符串数组（如果没有，则返回空数组 []）。
```

缺陷：只说"文本中包含的任务"，**未界定待办主语必须是用户本人**。新闻正文里确实"包含要执行的任务"——只是执行者是新闻当事人（警方）。模型忠实照抽，于是产生"警方继续追查其他涉案青少年""荃湾警区反黑组第一队跟进后续调查"这类与用户无关的待办。这不是逻辑 bug，是 prompt 的语义边界太宽。

放大因素：
- 默认场景是"高效职场人"（`ScenePreset.swift:112` → `.professional`），其 `enableTodos = true`（`:80-81`），所以随手拍默认都会走待办提取。
- `outputLanguageDirective`（`AIPromptProvider.swift:82`）只管输出语言、不管待办归属。
- 新闻/纪实类文本天然充满"某方将采取某行动"的句式，命中率高。

### 改动 B 的根因（截断已核实）

`SparkAIService.swift` 的 `buildSystemPrompt`（`:494–526`）里两层拍记注入方式不同：

| 层 | 代码位置 | 发送内容 | 截断 |
|---|---|---|---|
| anchor（最近 15 条） | `:510-514` | 标题 + 日期 + 摘要 | `trunc(r.summary, 100)`；**`detailedContent` 根本不发** |
| semantic（语义命中） | `:515-522` | 标题 + 日期 + `recordFullText` | `trunc(body, 800)` |

（`anchorCount = 15`、`semanticLimit = 8` 见 `SparkRecordRecall.swift:20`。）

后果：一篇英文文章若落在 anchor 范围，Spark 只看得到标题 + 100 字摘要，看不到正文；即便走 semantic，全文也最多 800 字，不足以翻译整篇。Spark 能"找到"文章是因为标题/摘要命中召回，但真要翻译时手里没货。

### 关键纠正：不需要标题模糊匹配

"系统怎么知道 LLM 第二轮说的'就是这篇'指哪条拍记"——这个能力**代码里已经有了，且比标题匹配可靠**：

- Prompt 强制模型对每次引用打 `[来源N]` 标记（`SparkAIService.swift:614-620`）。
- `mapCitations`（`:478`）把 `[来源N]` 解析为 `Citation`，**每个 `Citation` 带稳定的 `recordID: UUID`**（`SparkModels.swift:12`）。
- 这些 citation 已挂在每条 assistant 消息上（`SparkViewModel.swift:250`），也进入 `ConversationRound.assistantMessage`。

所以"上一轮引用了哪条拍记"是**已知且精确（UUID 级）**的，无需去回复文本里反向猜标题（标题被意译就匹配不上）。`[来源N]` 是结构化标记，不受意译影响。改动 B 因此以 citation 为触发信号。

## 改动 A：待办提取 prompt 加语义边界

**目标**：新闻/资讯/文章等非个人内容不再产出待办；即使是个人内容，也只提取"用户本人需亲自执行"的项。

**文件**：`Notiee/Services/AIPromptProvider.swift`

**范围**：两个 target（免费版走 `BackendAIProcessingService`、Plus 走本地，但 prompt 都来自这个共享文件）。

### 步骤

1. 修改 `todos` 字段定义，加入三条约束，语义大致为：
   - **主语限定**：只提取"用户本人需要亲自执行"的任务/待办；若任务执行者是文本中提到的第三方（新闻当事人、机构、他人），不要提取。
   - **内容类型闸门**：若内容属于新闻、资讯、文章、纪实等非用户个人笔记/会议/计划的性质，`todos` 一律返回 `[]`。
   - **（可选）few-shot 反例**：给一个"新闻正文 → todos 应为空"的短示例，比纯描述更稳。

2. **三处语言分支必须同步改**，否则简/繁/英行为漂移：
   - `buildTextPromptZHHans`（约 `:177`）
   - `buildTextPromptZHHant`（约 `:151`）
   - `buildTextPromptEN`（约 `:124`）

   > 参考 HANDOFF 的既有教训（"SwiftUI 字面量即本地化 key，改一处要改三份 Localizable"）——此处同理，三份 prompt 要同改同措辞。

### 建议的新文案（简体，繁/英照此翻译）

```
"todos": 只提取【用户本人需要亲自执行】的任务或待办事项，提取为字符串数组。
以下情况必须返回空数组 []：
  - 任务的执行者是文本中提到的第三方（如新闻当事人、机构、他人），而非用户本人；
  - 内容属于新闻、资讯、文章、纪实等信息性内容，而非用户的个人笔记、会议或计划。
如果没有属于用户本人的待办，返回空数组 []。
```

### 风险与验证

- 纯文案改动，无逻辑/接口变化，风险低。
- 验证：用一条香港新闻图（如荃湾少年袭人）走一遍拍记流程，确认 `todos` 为空；再用一条真实会议/计划图，确认用户本人待办仍被正确提取（无回归）。
- 两 target 各验一次（免费版经后端 `/ai/process`，Plus 经本地处理）。

## 改动 B：短跟进（翻译/展开）时回灌被引用拍记的全文

**目标**：用户在上一轮 Spark 引用了某篇拍记后，发出"翻译一下 / 展开说说 / 详细讲讲"这类短跟进时，把该拍记的完整 `detailedContent` 注入当轮 prompt，让 Spark 真正拿到正文。

**文件**：`Notiee/Features/Spark/SparkAIService.swift`（共享）、`Notiee/Features/Spark/SparkViewModel.swift`；需验证 `BackendSparkAIService`（复用同一 `buildSystemPrompt`）。

**范围**：两个 target。

### 触发条件（三者同时满足才回灌，避免误触发正常新问题）

1. 用户本轮消息**很短**（阈值建议 <20 字）且像跟进/指代类（翻译、展开、详细说说、继续、它、这篇……）。可复用/借鉴 `SparkIntentDetector` 的判断思路。
2. **上一轮 assistant 消息的 `citations` 非空**——直接取其 `recordID`，无需解析文本。
3. 命中的 record 仍存在且未删除、未加密。

### 注入方式

- 在 `buildSystemPrompt` 新增一个板块，例如 `## 完整内容（用户正在追问的拍记全文）`，把这些被 pin 的 record 的 `detailedContent` **以高上限或不截断**（建议上限 ~4000 字）注入。
- 只灌"上一轮被引用的那几条"，不是整个召回集，以控 token。
- 该板块与既有召回块并存；anchor 块本就不发正文（`:513` 只发 summary），故回灌是纯补充、不冲突。

### 接口形态（二选一，推荐第一种）

**方案 B1（推荐）：给 `ask` / `buildSystemPrompt` 传 `pinnedRecordIDs: [UUID]`**
- 改动面小、语义清晰，`RecalledRecords` 保持不变。
- `buildSystemPrompt(recall:recentRounds:upcomingEvents:pinnedRecordIDs:)` 内部按 ID 从全量 records（或 recall 集）取全文，追加板块。
- 需同步 `SparkAIServicing` 协议签名（`:39`）、`BackendSparkAIService` 的转发（`:184` 附近）。

**方案 B2：扩展 `RecalledRecords` 增加 `pinnedFullTextRecords` 字段**
- 把"要全文注入的记录"作为召回结果的一部分。
- 改动更内聚于召回层，但 `RecalledRecords` 语义变重，且需要在 recall 阶段就知道 pin 信息（目前 pin 信息在 ViewModel 层才拿得到）。

> 倾向 **B1**：pin 的信号来自"上一轮 assistant 消息的 citations"，天然在 `SparkViewModel` 层可得，用参数下传最直接。

### 实现落点

- `SparkViewModel.processQuestion`（`:214-215`，recall 之后、调用 `ask` 之前）：
  1. 读 `messages` 中上一条 assistant 消息的 `citations`；
  2. 判断本轮 `q` 是否满足触发条件（短 + 跟进/指代）；
  3. 满足则算出 `pinnedRecordIDs`，随 `ask` 下传。
- `SparkAIService.ask`（`:184`）与 `buildSystemPrompt`（`:494`）：接收 `pinnedRecordIDs`，取全文（用 `recordFullText` 或直接 `detailedContent`）追加板块。
- `BackendSparkAIService`：确认其 `ask` 路径同样把 `pinnedRecordIDs` 透传给共享的 `buildSystemPrompt`。

### 局限（保留，属预期）

- 只覆盖"上一轮被引用过的拍记"，不跨多轮。
- 是启发式触发。但绑定 UUID，比标题匹配可靠——不受标题意译影响。
- token 成本上升有限（只在命中跟进时、只对被引用的少数记录注入全文）。

### 验证

- 造一篇正文较长的文章拍记（确保其 `detailedContent` 长于 800 字），让它落在 anchor 范围。
  1. 第一轮问"最近有什么关于 X 的文章"，确认 Spark 引用它并出现 `[来源N]` / citation。
  2. 第二轮发"翻译一下"，确认 prompt 里出现"完整内容"板块且含完整正文，Spark 能翻译整篇而非只翻标题/摘要。
- 反例：正常新问题（长、非指代）不应触发回灌，确认无关全文未被注入。
- 两 target 各验一次（免费版经后端 `/ai/chat`，Plus 走本地）。
