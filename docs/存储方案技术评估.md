# Notiee 存储方案技术评估

> **日期**: 2026-05-27  
> **评估人**: 基于源代码分析  
> **背景**: 当前使用 JSON 全量读写，随数据增长需考虑增量存储方案

---

## 1. 现状分析

### 1.1 当前方案：JSON 全量文件

```
存储目录: Application Support/Notiee/
├── records.json          # [NoteRecord] — 所有拍记记录
├── folders.json          # [CustomFolder]
├── tags.json             # [EventTag]（含标签映射编码）
└── custom_events.json    # [ScheduledEvent]
```

**写入方式**：
- 每次 `persistRecords()` 调用将**整个 `[NoteRecord]` 数组**序列化为 JSON 并原子写入磁盘
- 每个 mutation 操作（toggleFavorite、toggleDeleted、updateRecord 等）都触发全量写入

**协议隔离**：
```swift
protocol NoteRecordPersisting {
    func loadRecords() throws -> [NoteRecord]
    func saveRecords(_ records: [NoteRecord]) throws
}
```
所有持久化通过协议注入，替换后端只需实现新协议。

### 1.2 性能估算

| 记录数 | JSON 大小（估算） | 写入耗时（估算） |
|--------|------------------|-----------------|
| 100 | ~50 KB | < 5ms |
| 500 | ~250 KB | ~15ms |
| 1,000 | ~500 KB | ~30ms |
| 5,000 | ~2.5 MB | ~150ms |
| 10,000 | ~5 MB | ~300ms+ |

**结论**：1000 条以内性能可接受。超过 3000 条后，每次写入开始明显卡顿（@MainActor 上下文）。

## 2. 候选方案

### 2.1 SwiftData（Apple 原生）

| 维度 | 评估 |
|------|------|
| **最低系统** | iOS 17.0+（项目要求 iOS 18.0，✅ 满足） |
| **集成成本** | 极低，无需第三方依赖 |
| **增量更新** | 原生支持，`@Model` 自动生成 schema |
| **查询能力** | `#Predicate` + `@Query`，支持排序/过滤 |
| **iCloud 同步** | 内置 CloudKit 同步（NSPersistentCloudKitContainer） |
| **Migration** | 轻量级自动 migration，复杂变更需手动 |
| **社区成熟度** | iOS 17/18 有若干已知 bug（predicate 限制、relation lazy load） |
| **适用场景** | 结构化数据，关系模型简单 |

**优点**：
- Apple 原生，长期支持
- 4 行代码即可定义模型（`@Model`）
- 自动化 diff + 增量写入
- 原生 iCloud 同步

**缺点**：
- 新框架尚有坑（复杂的 `#Predicate` 编译错误）
- 数据不透明（没法直接打开文件看 JSON）
- 调试困难（sqlite 文件需要模拟器导出）
- 已有记录的 migration 需要手动处理

### 2.2 GRDB.swift（SQLite 封装）

| 维度 | 评估 |
|------|------|
| **最低系统** | iOS 13.0+ ✅ |
| **集成成本** | SPM 添加，需定义 Table 和 Column |
| **增量更新** | SQLite 原生 UPDATE/DELETE/INSERT |
| **查询能力** | 完整 SQL + 类型安全查询接口 |
| **性能** | 极佳，SQLite 基准 |
| **社区** | GitHub 6.6K star，活跃维护 |
| **适用场景** | 大数据量、复杂查询、关联查询 |

**优点**：
- SQLite 底层，成熟稳定
- 精细的增量控制
- `ValueObservation` 支持响应式数据更新
- 数据文件可用任何 SQLite 工具直接查看

**缺点**：
- 需要手写 Table 定义和 Migration
- 比 SwiftData 集成成本高
- 无原生 iCloud 同步（需 CloudKit 自实现）

### 2.3 当前方案优化（JSON + 增量写入）

**不在现有方案上优化**的理由：
- JSON 全量写入在原协议下已是最简实现
- 做增量 JSON（追加行）违背 JSON 格式本身的设计
- 不如直接迁移到数据库

## 3. 推荐方案：GRDB.swift（分阶段迁移）

### 3.1 选择理由

1. **稳定性优先**：SwiftData 仍在快速迭代（iOS 17 → 18 有大改），GRDB 基于 SQLite 极其稳定
2. **协议兼容**：当前 `NoteRecordPersisting` 协议可以直接实现 GRDB 版本
3. **渐进迁移**：可以先双写（JSON + GRDB），验证无误后切换到 GRDB
4. **调试友好**：.sqlite 文件可直接用 TablePlus 等工具查看
5. **查询优势**：搜索功能当前是纯内存 `filter`，未来可以 SQL FTS5 全文索引替代

### 3.2 迁移路线图

```
Phase 1（MVP 发布后）：
  - SPM 添加 GRDB.swift
  - 实现 GRDBNoteRecordStore: NoteRecordPersisting
  - 首次启动自动从 JSON 迁移数据到 SQLite
  - 保持 JSON 文件作为备份

Phase 2：
  - 所有读写切换到 GRDB
  - 删除 JSON 文件（或保留作为导出用）
  - 添加 FTS5 全文索引优化搜索

Phase 3（可选）：
  - GRDB ValueObservation → SwiftUI @Published 自动刷新
  - 增量同步（只上传变更记录到 iCloud）
```

### 3.3 GRDB 数据表设计

```sql
CREATE TABLE records (
    id TEXT PRIMARY KEY,
    event_id TEXT,
    folder_id TEXT,
    captured_at REAL NOT NULL,
    image_paths_json TEXT NOT NULL DEFAULT '[]',
    title TEXT NOT NULL,
    ocr_text TEXT NOT NULL DEFAULT '',
    summary TEXT NOT NULL DEFAULT '',
    detailed_content TEXT NOT NULL DEFAULT '',
    processing_state TEXT NOT NULL DEFAULT 'pending',
    key_points_json TEXT NOT NULL DEFAULT '[]',
    definitions_json TEXT NOT NULL DEFAULT '[]',
    is_favorite INTEGER NOT NULL DEFAULT 0,
    is_deleted INTEGER NOT NULL DEFAULT 0,
    edited_at REAL,
    models_used_json TEXT,
    token_usage INTEGER NOT NULL DEFAULT 0,
    device_name TEXT
);

CREATE TABLE todos (
    id TEXT PRIMARY KEY,
    record_id TEXT,
    content TEXT NOT NULL,
    is_completed INTEGER NOT NULL DEFAULT 0,
    created_at REAL NOT NULL,
    due_date REAL,
    has_reminder INTEGER NOT NULL DEFAULT 0,
    FOREIGN KEY (record_id) REFERENCES records(id)
);

CREATE TABLE folders (
    id TEXT PRIMARY KEY,
    name TEXT NOT NULL,
    created_at REAL NOT NULL
);

CREATE VIRTUAL TABLE records_fts USING fts5(
    title, ocr_text, summary, detailed_content,
    content='records', content_rowid='rowid'
);
```

## 4. 临时建议

**当前阶段保持 JSON**，原因：
1. MVP 阶段数据量可控（< 1000 条）
2. 协议已隔离，换后端不影响业务代码
3. JSON 文件可读性好，方便调试和手动修复
4. 备份/导出（.tmn 格式）依赖 JSON 序列化，保留能力
5. 等 MVP 数据量增长到触发阈值时再执行 Phase 1 迁移

**触发条件**：单次 `persistRecords()` 耗时 > 50ms 或 records.json > 2MB。

---

> **决策**: 保持 JSON 方案，在 `NoteRecordPersisting` 协议下准备 GRDB 实现，条件触发时切换。
